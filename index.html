PraxisAnswer#4

看完代码了。结论先说：不是算法思路错，是复杂度结构和 Houdini 不一样——你这里是"每轮全量重建 + 串行全网格验证"，Houdini 是"一次性建队列 + 批量塌陷 + 只刷新受影响的局部"。这个差别在小网格上无所谓，一上十万面就指数级拉开。

三个真正的瓶颈

  1. 候选验证是 O(T) 全网格扫描，而且是串行的。主循环 collapse.rs:1070 里每个 candidate 都要过 collapse_is_valid，而它第一步 validation.rs:11 的 collapsed_triangle_keys_are_unique 会把所有 active 三角形扫一遍塞进 HashSet。内部边的塌陷几乎永远不产生重复三角形，所以 .all() 从不提前退出，每个 candidate 都是完整 O(T)。一个 pass 里候选是 O(E) 个，于是每轮 O(E·T)，且这段在 for candidate in candidates 串行循环里，Rayon 帮不上忙。10 万面网格 E≈30 万、T≈10 万，光这一个函数一轮就是 3×10^10 次操作。

  2. 每轮全量重建，最多 256 轮。build_candidates（collapse.rs:1078）每轮从零重建 DecimationTopology、point-to-triangle 邻接、所有三角形平面，然后重新给每一条边打分、重建整个队列。而你每轮只塌一个"互不相邻"的独立集（used[] 冲突检查），大幅减面需要很多轮，每一轮都付一次全量重建的钱。Houdini 是 populateQueue 一次，之后 fetchNextCollapseBatch → 批量 commit → refreshCollapseData 只重算受影响 half-edge 的 cost 并原地更新堆记录（你们 reverse 文档里已经写了这条证据链）。

  3. 打分里有 O(E) 全局扫描，默认开启。score_candidate 里无条件调 add_edge_quadric_planes（scoring.rs:803），它对每个端点都 topology.edges().iter().filter(...) 扫全边表；endpoint_touches_seam（scoring.rs:830）在默认 vertex_attribute_seam_weight=1.0 下对每个非 seam 边再扫两遍全边表。即使网格根本没有 seam/boundary，这两次 O(E) 扫描照付，合起来每轮 O(E²)。打分本身是 Rayon 并行的，所以这块没前面那个串行瓶颈痛，但也是实打实的浪费。

次要的还有：每轮 clean_working_triangles 全量 O(T) HashSet 清理，以及 primary 路径里 collapse_surviving_point_count 每个 candidate 克隆全部 positions（collapse.rs:994）。

Houdini 快在哪：原生 GU_PolyReduce2::DecimatorT 是 half-edge 减面器，候选 cost 缓存、优先队列按 cost 排序、初始打分并行 splittable range、批量非冲突 collapse、之后只对 findPrimary 解析出的受影响 hedge 去重重算并原地更新堆。每轮成本是局部的，跟网格总量基本解耦。你们 reverse 报告 houdini_polyreduce_20_5_584_native_reverse.md 里"Consequences"一节自己也写着：greedy triangle-edge passes instead of the native queue plus non-conflicting batch and local refresh lifecycle。

最该改的三件事（按收益排序）：

  1. 把 collapsed_triangle_keys_are_unique 从全网格扫描改成一环邻域检查：point_to_tris 已经建好了，只对 keep/remove 的合并邻域做去重即可，从 O(T) 变 O(valence)。
  2. 给每个点预计算 incident edge 表，add_edge_quadric_planes 和 endpoint_touches_seam 直接查邻接，别再扫全边表。
  3. 把"每轮全量重建"换成脏边增量：记录每轮受影响边，下一轮只重算它们并原地更新堆。你们其实已经有 IndexedCollapseQueue 和 reduce_working_mesh_primary 实验路径（CUNNING_POLYREDUCE_PRIMARY_QUEUE_EXPERIMENT），它才是朝 Houdini 生命周期对齐的方向，只是产品路径还没切过去。

顺带一提：你们实验路径默认没启用，所以线上跑的还是最贵的那条 batch reducer。要我先做第 1 条（邻域验证）吗？那个改动最小、收益最直接，不用动整个生命周期。
